# ER-01 local Debug1 tools — ER-CH-contract-1

This is an independent live policy `household_plan_highs_live_pv_lstm_dm_v1`, not frozen FV costminTree or Release. Uses the existing site1 PV LSTM and DM checkpoints without training; LMS is explicitly disabled because VE ended history contains no observed weather. Official HA SOC is the current slot-boundary energy and is conservatively rounded for planning. First-slot PV/load use the preceding ended interval's official HA observations held forward: they have a one-slot physical lag and no future leakage. A fresh HA poll does not make those powers instantaneous source-slot observations. Another 192 contiguous ended VE intervals feed the DM history. Forecast weather and prices use today's/tomorrow's read-only API, never `_actual_irr` or future actual load/PV. Existing DM repeats exogenous inputs four slots from the origin; this model interface has a known quarter-hour alignment limitation.

Actual local Debug1 physics is 5kWh/2kW, charge efficiency .95, discharge 1. Runtime reads and validates these against HA, instead of substituting the frozen FV 14kWh/5kW parameters. Software reserve constraints never write SOC protection entities.

Run from workspace: `python -m Anker_ChargingAndEnergyStorage.energy_runtime.server`. Standard library HTTP at fixed `http://127.0.0.1:19389`; no added dependency. Private credentials are `%LOCALAPPDATA%/AnkerEnergyRuntime/api.json` with `{url,token}`. Send token as `X-Energy-Runtime-Key`, never in query/log/project. Requests with Origin or an unexpected Host are refused. POST uses application/json. Existing site1 binding is supplied by the trusted channel as `owner:{ownerKey:<64 lowercase hex>,householdId:"site_1"}`; no untrusted natural-language target selection. All other households rejected.

| Tool | Input | Result |
| --- | --- | --- |
| GET /health | no token needed | schemaVersion `energy-runtime-v1`, environment `local_debug1_sim`, status ready/blocked, reason |
| GET /snapshot | authenticated | sourceSlot/sourceTime, physicalInputsKind/telemetryPhysicalAsOfSlot/socBoundarySlot, identity, ha official telemetry/control readback, three site physical identities, targetWindow |
| POST /proposal | `{owner,effectiveConstraints,requestId}` | immutable full proposal; identical request id returns previous; changed constraints version rejected |
| POST /confirm | `{owner,episodeId,proposalId,confirmationId}` | full episode receipt; identical confirmation returns previous without writes |
| GET /episode?episodeId=…&ownerKey=… | authenticated, owner matches | persisted receipt, read only |
| POST /reconcile | `{owner,episodeId}` | read-only evidence reconciliation; never resends a battery action |
| POST /stop | `{owner,requestId}` | fixed site1 zero action, HA+nexttick verified; persisted idempotent result stopped/unknown |

`targetWindow` comes directly from snapshot: `{start:"2025-06-03T00:00:00",end:"2025-06-05T00:00:00",timeBasis:"device_local_naive",timezone:null}`. It must exactly match effectiveConstraints. User real UTC activities are not shifted into the old simulated calendar; dated constraints reject with time_basis_unknown. Only timeless `type:"reserve_soc",value:{minimumPercent:0..100}` is supported. All typed memories are supplied, none silently dropped. Unsupported/rejected hard constraints reject the whole proposal with explicit IDs/reasons. contextOnlyMemoryIds are not consumed and missing fields do not invent energy demand. Envelope schema is ch02-effective-constraints-v1, with memoryVersion/constraintsVersion/usedMemoryIds/constraints as agreed in CH02.

Both snapshot and forecast.provenance identify the power input as `physicalInputsKind:"previous_ended_interval_hold",telemetryPhysicalAsOfSlot:sourceSlot-1`; `socBoundarySlot:sourceSlot` identifies the SOC energy boundary. `sourceTime` is the simulator clock at that boundary, while HA reported_at/captured_at and snapshot capturedAt are poll/capture times. None substitutes for the physical power interval. Before any interval ends, snapshot reports initial_sim_state and null telemetryPhysicalAsOfSlot; forecast still requires 192 ended intervals. Consumer measurementSourceSlot maps to telemetryPhysicalAsOfSlot.

Proposal has `episodeId`, `proposalId`, `expiresAt` (Unix seconds, 10 minutes), `sourceSlot`, `policyId`, `environment`, `sourceSnapshot`, `constraintsVersion`, `memoryVersion`, `usedMemoryIds`, `consumedMemoryIds`, `unsupported`, `rejectedMemoryIds`, `reserveEnergyKwh`, `forecast`, `plan`, `expectedCostEur`, `events` and `execution`. Each plan row has `charge_kw,discharge_kw,import_kw,export_kw,energy_kwh,curtail_kw,must_kw,new_kw`; power is kW, energy is kWh at slot end. Forecast is a horizon calculation, not a saving guarantee. The UI must show the exact `execution:{targetPowerW,sourceSlot,intervalMinutes:15,intervalCount:1,signConvention:"negative_charge_positive_discharge"}` before confirmation. Only this first interval executes; later horizon rows need a new proposal/confirmation.

Confirmation requires still-paused identical local container/plugin identity and sourceSlot, unchanged official SOC, a valid plan, no unresolved prior execution and matching owner/proposal/expiry. Channel must recheck its current memory/constraintsVersion before submitting a stored confirmation. HTTP200 from HA is submitted only. The controller waits for official target readback, invokes the **sim clock step only**, then requires next-slot official target/SOC/battery readings and VE applied setpoint/physical energy/cost. Other two stations' setpoints remain unchanged. All battery writes use the existing local HA webhook and official plugin. No Modbus, VE control/mode or SOC entity writes.

Successful `events[].stage` is proposed → confirmed → dispatched → acknowledged → settled → outcome. `dispatch:{requestId,environment,sourceSlot,targetPowerW,veBeforeAll,preparedAt}` is durably saved before dispatch. Successful `evidence` includes `requestId` (=episodeId), sourceSlot/nextSlot, `readbackMatches:true`, `settlementAvailable:true`, `evidenceKind:"simulator_settlement"`, `intervalCostEur`, capacityKwh/dtHours/effCharge/effDischarge, targetPowerW, HA before/after, exact VE before/after, ended historyRow, prices and otherSites before/after. History power is rounded 0.1W, SOC 0.1%, cumulative cost 4 decimals; exact VE state supplies unrounded SOC and cum_cost_eur. State PV/load are next-slot values and never mixed into the ended-slot balance. `outcome:{kind:"local_sim_single_interval",settlementAvailable:true,intervalCostEur,reserveMet:true,savingsClaim:"not_evaluated"}`.

Missing proof never creates acknowledged/settled events. A failed/unknown dispatch is never retried; failure requests pause and HA site1 zero, requiring official and next-tick zero readback before `stopEvidence.zeroPowerVerified:true`. GET episode does not itself reconcile. Explicit POST reconcile can complete only when a unique next-tick proof is still available; otherwise retains unknown and records read-only observedSlot/reason. An unresolved unknown blocks later execution. Restart cannot silently replay it.

Focused checks: `python -m unittest Anker_ChargingAndEnergyStorage.energy_runtime.test_runtime -v`. These use real HiGHS for model constraints and isolated adapters for lifecycle; they do not prove HA execution. Live evidence and independent oracle are separate in checks/runtime. No real household/contest/remote environment is authorized.

RD-01 adds POST /preview, GET /decision and optional proposal.previewId. The exact producer contract and synthetic parser JSON are in docs/specs/路演联动展示/core-interface.md and core-interface.sample.json. A preview captures one frozen origin/forecast and solves the current confirmed floor versus one explicit hypothetical reserve; it never creates an executable episode, writes Assistant memory or sends a command. Parent previews reuse existing verified inputs. Infeasible/unchanged results remain visible. Saving the candidate is separate; a new actual proposal can reuse the frozen verified LP only when actual confirmed constraints and physical origin match. Unsupported fields, changed other reserves, stale origin and changed request payloads reject.

GET decision uses one mode=ro SQLite transaction without the execution lock or adapter calls; even dispatched during a long confirmation is readable. The projection contains immutable origin observations, per-slot forecast/plan, safe typed constraint summaries, and only the saved verified receipt as actual. It contains no owner credentials, user prose or confirmation token. viewVersion is producer canonical SHA256; Service enrichment must use the same algorithm. Old records without summaries keep empty items rather than reconstructing historical personal values.

Initial snapshot.observation reads matching previous-ended VE grid history plus official HA power/SOC/target and simulator source-hour price, preserving fieldSources and distinct physical/poll/price times. Missing grid/price stays null; no balance inference or solver runs on GET. All preexisting execution/unknown/stop restrictions continue to apply.

## Release environment pipeline candidate (offline only)

The new `release.py` reuses `DJXZ/AnkerProject_DJXZ_Release/Simulator` without modifying that package, its main loop or the optimizer. It is a separate, opt-in read source: App `GET /api/assistant/environment` → authenticated owner/session read → `RuntimeAPI.environment_snapshot()` → loopback `GET /environment/snapshot` → `ReleasePipeline` → original SolarBank entity mapping and HA client. App/Feishu may explicitly ask `环境机状态`; existing `家里现在怎么样` and plan/confirm tools continue to use the original local Debug1 environment. The new endpoint grants no pending seen token, clears no request cache and never changes the selected local decision.

No configuration file is created or activated by this work. The only optional private file is `%LOCALAPPDATA%/AnkerEnergyRuntime/release-pipeline.json`. Its schema (field names only) is in [contract](../../docs/specs/环境机管线接入/contract.md). Missing file or `enabled:false` returns `disabled` before constructing any HA/Simulator client. Explicit enabled configuration requires independent HA and dashboard credentials, all three exact site suffixes, bounded timeout and validated fixed endpoints. It never reads team `ha_token.txt`, copies main.py's address/password defaults or accepts a URL/entity/power from App input. Client proxy inheritance and redirects are disabled; HA writes are configured for one attempt, although this candidate exposes no remote write path.

`environment-pipeline-v1` is always labelled `release_official_ha_unverified`, `householdId:site_1`. A complete response is `ready` only in the sense that required HA fields are present; `validation` remains false and control remains disabled. Missing/unknown/unavailable/nonfinite/out-of-range/wrong-unit fields become null with `partial`, including missing SOC, rather than silently becoming zero. Only the bound household is projected, with kW/%/W units and a separate naive device time; `observedAt` is capture wall-clock seconds and proves neither freshness nor time identity. No URL, entity suffix, token, dashboard telemetry or other household is projected. Prices remain null because the exact competition input/time contract has not been accepted. Transport errors return a sanitized `unavailable`, clearing stale UI data.

The pure `command_from_plan` reuses the team's protocol with reviewed `charge_kw`, `discharge_kw`, **`export_kw`** and current sell price. Charge targets total battery charging; discharge targets grid export. It rejects bad/over-limit/round-to-zero values and unsupported self-use discharge instead of passing the local signed battery target or silently clamping a plan. `dispatch()` always rejects `release_execution_contract_unverified`; no App POST, loopback POST or Agent command enables it. Before a later control implementation, verify next-tick acknowledgement, single-interval exit and unique settlement evidence in the actual environment. Existing local settlement checks are not weakened or reused to claim remote completion.

This candidate was validated only with fake responses, temporary files/owners and socket/process-denied offline checks. Running services and current served frontend were not restarted or changed. No network, health, HA, Docker, model or environment-machine test was run. Focused command: `python -X utf8 -B -m unittest Anker_ChargingAndEnergyStorage.energy_runtime.test_release -v` (from workspace root); it does not prove connectivity or execution.
